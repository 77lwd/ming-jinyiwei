# 《我在明朝当锦衣卫》1-3月 MVP 游戏开发规格

> 版本：1.0  
> 日期：2026-08-15  
> 状态：待用户确认  
> 适用范围：序章至第3月结束

## 1. 文档定位

本文档是《我在明朝当锦衣卫》第一版可玩 MVP 的产品与技术规格，是后续实施计划、代码和验收的直接依据。

现有《游戏设计文档》继续作为完整120个月世界观、人物和剧情素材库；旧版及 v2 实现计划不再作为 MVP 的执行依据。若文档之间冲突，以本规格为准。

## 2. 产品目标

制作一个可在电脑和手机浏览器中离线运行的单机文字 RPG。玩家经历五幕序章，并完整游玩崇祯元年的第1至第3月，理解以下四个核心体验：

1. 时间有限：每月只有3点行动力。
2. 调查有代价：获取线索会消耗资源并提高暴露风险。
3. 关系会改变道路：NPC不是数值奖励，而是未来路线与情感代价。
4. 选择必须被叙事回应：每次行动和剧情选择都产生可见结果，而不只是后台数值变化。

MVP成功的标准不是内容数量，而是玩家能够无障碍完成一次“序章 -> 月度行动 -> 获得线索 -> NPC剧情选择 -> 第3月结束 -> 存档恢复”的完整流程。

## 3. 设计原则

- 剧情为主，策略为辅。数值负责制造选择，不取代叙事。
- 固定主线节点保证节奏，月度行动决定玩家到达节点时拥有的能力和关系。
- 所有规则在引擎层生效，界面只负责展示，不承担业务约束。
- MVP只实现会被玩家实际体验的系统，不提前实现完整120个月内容。
- 数据结构必须支持后续扩展至15个主线节点和9个结局。

## 4. 世界观与时间线修订

### 4.1 正史边界

游戏采用“以明代制度和崇祯时期为基础的架空历史”。真实官制和社会背景用于增强可信度，人物、案件及部分政治事件为虚构内容。

### 4.2 统一时间线

- 万历四十一年（1613）：3岁的廖威达遭遇灭门，李慕尘将其救出。
- 天启年间（1621-1627）：当年的商税输送网络在阉党庇护下扩张，逐渐连接祥云商行、景王府与东厂。
- 崇祯元年（1628）：18岁的廖威达以锦衣卫百户身份进入北镇抚司，游戏开始。
- 完整游戏计划覆盖崇祯元年至崇祯十年，共120个月。

此修订解决原设计中“天启六年灭门”与“崇祯元年已经过去15年”无法同时成立的问题。序章正文优先使用“十五年前”，避免堆砌年代说明。

## 5. MVP范围

### 5.1 必须包含

- 五幕序章及跳过功能。
- 新游戏、继续游戏和重新开始。
- 第1、2、3月的完整月度循环。
- 每月3点行动力，行动力不可跨月累计。
- 公务、训练、社交、调查、赚钱五类行动。
- 武力、智谋、口才、声望、财富、风险值。
- 周寒川与冯天顺的关系值。
- 烧焦木牌线索及清晰度。
- 第3月“重逢故友”主线节点和四个选择。
- 行动结果、选择结果及最近事件记录。
- 版本化自动存档和损坏存档回退。
- 桌面与移动端响应式界面。
- 离线启动和安装型 PWA 基础能力。
- 第3月完成页，可重新开始或返回查看最终状态。

### 5.2 明确不包含

- 第4月以后的主线剧情。
- 完整技能树、装备、战斗模拟和随机战斗。
- 柳如烟爱情线及其他完整 NPC 支线。
- 完整15节点和9结局系统。
- 多存档、云存档、账号、服务器和联网排行榜。
- 付费、广告、社交分享和数据分析服务。

MVP结束页是“第一章完成”，不是完整游戏结局。

## 6. 玩家流程

```text
启动应用
  -> 有有效存档？
     -> 是：继续游戏 / 重新开始
     -> 否：开始游戏
  -> 五幕序章
  -> 第1月引导行动
  -> 月末获得烧焦木牌
  -> 第2月自由行动
  -> 进入第3月时触发“重逢故友”
  -> 选择如何对待冯天顺
  -> 完成第3月自由行动
  -> 第一章完成页
```

### 6.1 月度循环

每个月遵循同一状态机：

```text
month_start
  -> scheduled_event（如有）
  -> action_selection
  -> action_result
  -> action_selection（行动力仍大于0）
  -> month_end
  -> monthly_event（如有）
  -> next_month / chapter_complete
```

- 玩家可以在行动力未耗尽时提前结束本月，但系统必须进行二次确认。
- 任何行动执行后立即自动存档。
- 剧情节点未完成时不能推进月份。
- 同一剧情节点只能完成一次。

## 7. 三个月内容设计

### 7.1 序章：十五年前的夜晚

五幕按顺序呈现：温暖的家、黑衣人突袭、母亲牺牲、李慕尘救人、十五年成长蒙太奇。序章建立复仇动机，但不一次性解释幕后势力。

玩家可逐幕继续，也可以使用“跳过序章”。跳过不会漏掉任何状态奖励。

### 7.2 第1月：进入北镇抚司

目标：教会玩家行动系统并给予第一条线索。

- 月初：周寒川带领廖威达熟悉北镇抚司。
- 第一个行动固定为“随周寒川巡街”，消耗1点行动力，获得5两和少量声望。
- 剩余2点行动力由玩家自由分配。
- 月末：整理父亲遗物时发现烧焦木牌，获得线索 `charred_trade_token`，清晰度为“模糊”。
- 叙事提示只说明木牌上能辨认出“云”“商行”，不提前揭示祥云商行全名。

### 7.3 第2月：第一次自由规划

目标：让玩家理解不同成长方向的机会成本。

- 玩家拥有完整3点行动力。
- 解锁针对烧焦木牌的调查行动。
- 本月不设置强制主线节点。
- 月末展示简短总结，说明廖威达正在锦衣卫站稳脚跟。

### 7.4 第3月：重逢故友

目标：证明关系选择会产生可见、可保存的后果。

- 进入第3月时自动触发“重逢故友”。
- 剧情节点解决后，玩家继续使用本月3点行动力。
- 若关系达到条件，解锁“与冯天顺喝酒”。
- 本月结束后进入“第一章完成”页面。

四个选择：

| 选择 | 结果 |
|---|---|
| 邀他喝酒叙旧 | 冯天顺关系 +40，解锁喝酒行动 |
| 礼貌寒暄 | 冯天顺关系 +20 |
| 敷衍离开 | 冯天顺关系 -10 |
| 询问父亲旧案 | 冯天顺关系 +10，设置 `told_feng_about_investigation` |

每个选择必须先展示 `outcomeNarrative`，玩家确认后才能返回月度行动。

|---|---|---:|---:|---|---|
| `patrol_duty` | 巡街执勤 | 公务 | 1 | 始终可用 | 声望 +2，财富 +5 |
| `handle_case` | 协助办案 | 公务 | 1 | 始终可用 | 智谋 +1，声望 +3 |
| `practice_blade` | 练习刀法 | 训练 | 1 | 始终可用 | 武力 +2 |
| `read_case_files` | 研读卷宗 | 训练 | 1 | 始终可用 | 智谋 +2 |
| `practice_speech` | 练习应对 | 训练 | 1 | 始终可用 | 口才 +2 |
| `visit_zhou` | 拜访周寒川 | 社交 | 1 | 周寒川关系 >= 10 | 周寒川关系 +8 |
| `drink_with_feng` | 与冯天顺喝酒 | 社交 | 1 | 冯天顺关系 >= 20，财富 >= 5 | 冯天顺关系 +10，财富 -5 |
| `investigate_token` | 调查烧焦木牌 | 调查 | 2 | 已获得木牌，财富 >= 8 | 财富 -8，智谋 +1，风险 +1，提升线索清晰度 |

行动结果必须包含短叙事文本。重复行动可以使用同一基础文本，但事件记录要包含发生月份和效果摘要。

## 9. 数值规则

- 属性范围：`0..100`。
- NPC关系范围：`-100..100`，MVP界面可隐藏具体下限说明。
- 风险范围：`1..5`，MVP初始值为1。
- 财富不得低于0。
- 行动力范围：`0..3`。
- 所有效果经过统一钳制函数处理。
- 条件不满足、行动力不足或剧情状态不允许时，引擎返回结构化失败原因，不静默失败。
- MVP不引入随机成功率；同一状态和选择必须产生同一结果。

## 10. 数据模型

### 10.1 条件和效果

条件与效果均采用判别联合，禁止使用大量可选字段和非空断言。

```ts
type Condition =
  | { type: 'attribute_gte'; attribute: keyof Attributes; value: number }
  | { type: 'wealth_gte'; value: number }
  | { type: 'relation_gte'; npcId: NpcId; value: number }
  | { type: 'risk_lte'; value: number }
  | { type: 'flag_is'; flag: string; value: boolean }
  | { type: 'has_clue'; clueId: string }
  | { type: 'month_is'; value: number }

type Effect =
  | { type: 'attribute_change'; attribute: keyof Attributes; delta: number }
  | { type: 'wealth_change'; delta: number }
  | { type: 'relation_change'; npcId: NpcId; delta: number }
  | { type: 'risk_change'; delta: number }
  | { type: 'set_flag'; flag: string; value: boolean }
  | { type: 'add_clue'; clue: Clue }
  | { type: 'upgrade_clue'; clueId: string; clarity: ClueClarity }
```

### 10.2 游戏状态

```ts
interface GameState {
  month: 1 | 2 | 3
  phase: 'prologue' | 'month_start' | 'action' | 'event' | 'result' | 'complete'
  prologueScene: number
  attributes: Attributes
  wealth: number
  actionPoints: number
  clues: Clue[]
  npcRelations: Record<NpcId, number>
  riskLevel: 1 | 2 | 3 | 4 | 5
  flags: Record<string, boolean>
  activeEventId: string | null
  currentNarrative: NarrativeBlock
  recentEvents: NarrativeEvent[]
}
```

`recentEvents`只保存最近20条记录，避免存档无限增长。完整120月版本是否保留全历史在后续规格中决定。

### 10.3 命令结果

所有状态操作返回明确结果：

```ts
type CommandResult =
  | { ok: true }
  | { ok: false; reason: 'not_enough_ap' | 'locked' | 'invalid_phase' | 'not_found' }
```

即使界面错误地发送命令，引擎也不能执行被锁定的行动或选择。

## 11. 叙事系统

叙事区是主界面中心，不是装饰组件。

- `currentNarrative`显示当前事件、行动结果或月度总结。
- `recentEvents`提供最近经历列表，玩家可回看但不能改变历史。
- 行动执行顺序为：校验 -> 应用效果 -> 生成效果摘要 -> 设置叙事 -> 自动存档。
- 剧情选择顺序为：引擎重新校验条件 -> 应用效果 -> 显示结果 -> 玩家确认 -> 标记事件已完成。
- 内心独白使用独立段落类型，不依赖解析星号判断样式。

叙事数据采用结构化段落：

```ts
interface NarrativeBlock {
  title?: string
  paragraphs: Array<{
    kind: 'prose' | 'dialogue' | 'monologue' | 'system'
    text: string
  }>
}
```

## 12. 存档设计

存档键：`ming_jinyiwei.save.v1`

```ts
interface SaveEnvelope {
  version: 1
  savedAt: string
  state: GameState
}
```

- 每次有效状态变化后自动保存。
- 加载时验证版本和核心字段，不能直接信任 `JSON.parse` 的结果。
- 存档损坏时保留原始值，提示玩家“存档无法读取”，并允许开始新游戏。
- “重新开始”必须二次确认，然后创建全新状态。
- MVP不提供回档、多存档和导入导出。

## 13. 界面与交互

### 13.1 桌面布局

- 左侧：月份、行动力、属性、财富、风险、线索和关系摘要。
- 中间：当前叙事，是视觉和阅读焦点。
- 右侧：可用行动或剧情选择。
- 剧情节点可使用覆盖层，但必须保持良好滚动和键盘操作。

### 13.2 移动布局

- 顶部紧凑显示月份、行动力和风险。
- 中部为可滚动叙事区。
- 底部固定主要操作入口，行动列表使用抽屉或底部面板。
- 属性、线索和关系放入“状态”面板，避免挤压正文。
- 支持宽度320px及以上，不允许横向滚动和文字遮挡。

### 13.3 视觉方向

- 深墨背景、宣纸正文、暗红重点色，并用绿色、金色区分安全与资源状态。
- 正文优先使用系统可用中文衬线字体；离线时不得依赖 Google Fonts。
- 动画保持克制：淡入、翻页和轻微墨迹过渡，并尊重 `prefers-reduced-motion`。
- 图标使用项目选定的图标库；不使用 emoji 作为正式操作图标。

### 13.4 可访问性

- 所有按钮可使用键盘操作，并具有清晰焦点状态。
- 颜色不是风险和锁定状态的唯一表达方式。
- 正文默认字号不小于16px，正文行高不小于1.7。
- 覆盖层打开时锁定背景焦点，关闭或完成后恢复焦点。

## 14. 技术架构

### 14.1 技术栈

- Node.js 20 LTS 或更高。
- React 18.x。
- TypeScript 5.x，启用严格模式。
- Vite 5.x。
- Zustand 5.x。
- CSS Modules。
- Vitest + React Testing Library。
- Playwright用于关键流程浏览器测试。
- `vite-plugin-pwa` / Workbox用于离线缓存和安装能力。

依赖必须在 `package.json` 中锁定兼容版本，并提交 lockfile；禁止以 `@latest` 作为可复现实施步骤。

### 14.2 模块边界

```text
src/
  app/          应用入口、页面状态和路由式切换
  engine/       条件、效果、命令和月份推进纯函数
  store/        Zustand适配、自动存档
  data/         行动、事件、NPC和初始状态静态数据
  components/   可复用界面组件
  features/     序章、月度行动、剧情节点、完成页
  styles/       全局变量和基础样式
  test/         测试工厂和共享设置
e2e/            Playwright完整流程
public/         PWA图标和静态资源
```

- `engine`不能导入React、Zustand或浏览器存储。
- `data`只声明内容，不修改状态。
- `store`调用引擎并负责持久化，不复制规则。
- 组件不能直接改写游戏状态，只能发送命令。

### 14.3 数据流

```text
玩家操作
  -> store命令
  -> engine校验条件与阶段
  -> engine返回新GameState或失败原因
  -> store提交状态并保存
  -> React根据状态重新渲染
```

## 16. 代码规范

- 使用ASCII英文作为代码标识符，中文仅用于内容和界面文本。
- 游戏数据ID使用稳定的 `snake_case`。
- React组件使用 `PascalCase`，函数和变量使用 `camelCase`。
- 不使用 `any`、非空断言或静默的 `default: return state` 掩盖非法数据。
- 纯函数不读取时间、随机数、localStorage或全局状态。
- 复杂规则通过命名函数表达，不在JSX中堆叠业务逻辑。

示例：

```ts
export function performAction(state: GameState, action: MonthlyAction): GameCommandResult {
  const failure = validateAction(state, action)
  if (failure) return { ok: false, reason: failure, state }

  const nextState = applyEffects(state, action.effects)
  return {
    ok: true,
    state: appendNarrative(nextState, action.narrative),
  }
}
```

## 17. 测试策略

### 17.1 引擎单元测试

- 每种条件的真、假和边界值。
- 每种效果及数值钳制。
- 锁定行动和锁定选择无法执行。
- 行动力扣除与提前结束月份。
- 第1月至第3月事件顺序。
- 节点只能触发一次。
- 相同输入产生相同输出。

### 17.2 状态与存档集成测试

- 新游戏初始化正确。
- 行动后叙事、数值和存档同步更新。
- 损坏存档和不支持版本安全回退。
- 刷新后恢复到操作前的准确阶段。
- 重新开始清除旧进度。

### 17.3 组件测试

- 不满足条件的行动和选项显示原因并禁用。
- 叙事段落按类型渲染。
- 剧情结果确认前不能继续。
- 移动端状态面板可访问。

### 17.4 浏览器端完整流程

至少覆盖两条路径：

1. 正常观看序章，完成三个月，选择与冯天顺喝酒，抵达完成页。
2. 跳过序章，中途刷新恢复，选择疏远冯天顺，仍可完成MVP。

同时验证桌面和宽度390px的移动视口，检查控制台错误、横向溢出、PWA资源及离线刷新。

## 18. MVP验收标准

- [ ] 首次启动可以开始游戏，存在存档时可以继续或重新开始。
- [ ] 五幕序章可逐幕阅读并可跳过。
- [ ] 玩家能够完整游玩第1、2、3月。
- [ ] 每月行动力正确重置为3且不能超支。
- [ ] 第1月末必定获得烧焦木牌。
- [ ] 第3月进入时必定且仅触发一次“重逢故友”。
- [ ] 四个冯天顺选择均产生不同的关系或flag结果。
- [ ] 每次行动和选择都显示结果叙事及效果摘要。
- [ ] 引擎拒绝绕过条件执行锁定操作。
- [ ] 刷新页面后能够准确恢复进度。
- [ ] 损坏存档不会导致白屏。
- [ ] 第3月结束进入“第一章完成”，月份不会推进到4。
- [ ] 桌面和390px移动视口无重叠、遮挡或横向滚动。
- [ ] 断网后已访问过的应用仍能启动并继续存档。
- [ ] `npm run test`、`npm run test:e2e`、`npm run typecheck`和`npm run build`全部通过。

## 19. 开发边界

### 始终执行

- 保留廖威达复仇主线、主要人物性格和选择代价。
- 规则先在引擎层实现和测试，再连接界面。
- 每个任务完成时运行对应测试，并保持应用可启动。
- 发现规格矛盾时先更新本文档，再修改代码。

### 需要重新确认

- 将范围扩大到第4月以后。
- 增加服务器、账号、云存档或联网功能。
- 删除核心人物或根本改变复仇主题。
- 引入会显著改变核心玩法的随机战斗或抽卡系统。

### 禁止事项

- 为赶进度跳过失败测试或删除验收条件。
- 在UI层重复引擎规则。
- 将存档或隐私数据发送到外部服务。
- 用临时占位文本冒充已完成剧情。

## 20. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 月度行动重复 | 玩家在第2月失去兴趣 | 每种行动提供明确叙事与不同成长价值 |
| 数值压过剧情 | 游戏变成刷属性 | MVP无随机成功率，节点选择以人物关系为核心 |
| 规则散落在UI | 后续15节点难扩展 | 所有校验集中在纯引擎命令 |
| 存档结构变化 | 更新后无法继续 | 从第一版使用版本化存档封装 |
| 移动端正文受挤压 | 阅读体验差 | 移动端采用叙事优先的单列布局 |
| 过早开发完整内容 | 返工成本高 | MVP验收通过前不录入第4月以后剧情 |

## 21. MVP之后

MVP通过并获得确认后，再为第4至24月编写独立规格。后续阶段复用本规格的数据契约和引擎，但不会在本次开发中预填完整剧情或结局。

下一份文档应是基于本规格拆分的实施计划，每项任务限制在约1至5个文件，并在每2至3项任务后设置可运行检查点。

# 开发工作流

本项目后续开发以玩家实际试玩反馈为核心。开始任何新阶段前，必须先展示计划并得到确认。

## 阶段开始前

1. 读取 `docs/playtest-feedback-round-2.md` 及后续试玩反馈文件。
2. 使用 `superpowers:brainstorming` 设计本轮要解决的体验问题，不直接开始写事件或改数值。
3. 提供两到三个可选方案，说明取舍和推荐方案。
4. 设计经玩家确认后，写入规格文档。
5. 使用 `superpowers:writing-plans` 创建可审阅的实施计划。
6. 计划必须写明：任务顺序、涉及文件、玩家需要决定或提供的内容、验收标准、不会改动的范围。
7. 只有玩家明确确认计划后，才能进入实现。

### 剧情与系统的共同设计门禁

- 在继续扩写第二章及以后章节前，必须先单独完成属性、养成、健康、银两、声望和人脉的总设计；风险系统已明确废弃，不得重新引入。
- 养成总设计必须明确每项数值的可感知作用、成长来源、限制、代价和跨章节变化，不能等剧情写完后再补。
- 已完成的章节稿中若只有临时资源钩子，状态必须标记为“待系统整合”，不得直接作为实施依据。
- 章节设计、养成设计和主线证据链完成交叉审查后，才能进入实施计划。
- 当前运行基线为“序章＋五章、固定章节主线和必要的阶段转折”；不再使用月份推进、风险、自由行动窗口、突发事件池、月度事件或可重复日常事件循环。

## 实现阶段

- 使用 `superpowers:test-driven-development`：先证明新行为当前不存在，再实现。
- 使用 `superpowers:executing-plans`：按确认计划逐项实施，在约定检查点汇报。
- 使用 `incremental-implementation`：每个可独立验证的切片完成后运行对应测试，不累计大批未经验证的修改。
- 使用 `frontend-ui-engineering`、`impeccable` 和 `ui-ux-pro-max`：当修改案件板、资源反馈、关系、选择或其他玩家可见界面时，先读取项目根目录的 `PRODUCT.md`，再审查信息层级、可读性和状态反馈。
- 使用 `code-review-and-quality`：在一次较大的阶段完成前做逻辑、可维护性、测试和回归风险审查。
- 使用 `documentation-and-adrs`：把玩家反馈、关键设计决定和阶段状态同步到文档。
- 代码发现优先使用项目代码知识图谱；需要理解跨模块关系时使用 `understand` 系列技能。

### 玩家可见 UI 重做流程

确认日期：2026-09-14。修改或重做游戏主界面、章节阅读、案件交互、状态反馈及结果页时，固定按以下顺序执行：

1. `Impeccable critique`：审查当前界面，明确保留、替换和废弃范围；
2. `Impeccable shape`：在写代码前确定信息架构、主要界面和交互流程；
3. `ui-ux-pro-max`：辅助校验排版、色彩、可读性、控件和体验规则；
4. `frontend-ui-engineering`：按确认设计实现生产质量的 React 界面；
5. `deprecation-and-migration`：移除已被新版替代的旧界面与旧展示入口；
6. `browser-testing-with-devtools`：在真实桌面浏览器中检查布局、交互、控制台与资源加载；
7. `Impeccable audit + polish`：完成可访问性、边界状态和最终视觉质量检查。

第一次执行以序章和第一章《纸灰里的银子》为试点。试点确认前暂停后续章节实现，不把第二章占位骨架或内部流程计数视为玩家可见成品。

## 不作为默认流程的工具

- 不使用浏览器自动试玩替代玩家试玩。浏览器工具仅在出现明确 UI 故障、布局问题、控制台错误或玩家要求复现时使用。
- 不使用内置生图。关键图片由玩家通过外部工具生成；收到图片后只负责验收尺寸、接入、缓存与布局。

## 玩家反馈处理

1. 玩家提出问题后，先逐条写进单独反馈文件，保留实际操作路径和具体数值。
2. 不把反馈压缩成笼统标题后立刻开工。
3. 先给出下一阶段设计和计划，等待确认。
4. 实现后交由玩家试玩；玩家反馈优先于自动化流程判断。

## 剧情与世界观设计自检

- 在向玩家提交任何剧情骨架、事件或角色设定前，逐项核对：该角色掌握信息的来源、其动机、行动导致结果的因果链、时间顺序，以及玩家在该节点实际能获知的内容。
- 不得用“主角恰好知道”“角色为了推进剧情而行动”或未说明的童年记忆弥补逻辑缺口。
- 每条关键线索必须能说明：它从何而来、为何在此时出现、谁能接触它、玩家如何验证它，以及错误理解它会造成什么后果。

## 角色设计自检

- 每个重要角色在进入剧情前必须写明：独立目标、恐惧或底线、关键关系、掌握与缺失的信息、当前处境，以及不依赖主角也会采取的行动。
- 角色不得只承担发任务、提供数值、解释设定、在固定时点背叛或牺牲等单一功能。其选择须能由既有动机和处境解释，并在后续剧情留下持续影响。
- 玩家应通过场景、行动和后果逐步认识人物；角色设定可以完整，但不得以旁白一次性透露其全部秘密或标签。
- 角色差异不能停留在年龄、身份、职业、创伤或几条背景资料不同，也不能把“独特灵魂”简化为剧情选项中的不同选择。人物必须先像真实活着的人：有自己的语言节奏、习惯、记忆、羞耻、偏见、幽默、矛盾、亲疏关系与不愿向人承认的部分；这些应自然流露于场景、对话和日常细节中。其行动和选择只是人物内在的结果，不能反过来代替人物本身。
- 讨论角色时，不得反复把人物压缩成“最看重什么”“会选哪一项”“属于哪种人”等抽象提问或二选一标签。优先从可感知的生活、关系、说话、行为、经历与矛盾中建立人物，再由此推导其在剧情中的行动。
- 人物基础设计阶段只讨论并确认角色的形象、性格、生活痕迹、关系与已知经历；不得过早天马行空地预写其后期剧情功能、命运、反转或宏大人物弧线。待人物基础定稳后，才可将其放入具体剧情因果中检验。
